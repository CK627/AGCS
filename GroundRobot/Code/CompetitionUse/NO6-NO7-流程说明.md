# NO6 / NO7 流程拆解

> `Auto-capture.py`（NO6）与 `Auto-capture-1.py`（NO7）的整体思路与完整过程。
> 两个脚本共用同一套骨架：一份 JSON 路线开车。差别只在「怎么知道目标在哪」。

---

## 1. 两个程序是什么关系

NO6 是基础版，NO7 是它的超集——NO7 里保留着 NO6 的全部逻辑，只在夹取前插了一段
自动精对准。所以 NO7 可以完全当 NO6 用（没有标定文件时自动降级）。

| | NO6 · `Auto-capture.py` | NO7 · `Auto-capture-1.py` |
|---|---|---|
| 行数 | 676 | 1038 |
| 定位 | IMU 积分航向 + 颜色块左右微调 | 阶段一 = NO6 全套；转弯后可选深度 ICP 校正航向 |
| 对准 | 到点摆好标准姿态，人看画面敲命令微调，回车夹 | 阶段二：ONNX YOLO 检测 bbox，雅可比矩阵把像素误差换算成舵机增量，自动居中 |
| 依赖 | 除路线 JSON 外不需要额外文件 | `calib_pick1/2.json`、`models/best.onnx`、可选 `models/map.npz` |
| 额外模式 | 无 | `--approach`（不用路线，模型直接靠近）、`--calibrate 1\|2`（标雅可比） |

## 2. 骨架：一份 JSON 驱动全部动作

主循环两个程序几乎逐字相同：读 `fixed_route.json`，按顺序执行。
**所有距离、角度、夹取脉宽都写在 JSON 里，代码里不写死任何点位**——
现场调路线就是改这个文件，不用改代码。

```jsonc
{"action": "forward",    "step": 100, "speed": 50}   // 前进 100mm
{"action": "back",       "step":  50, "speed": 50}   // 后退 50mm
{"action": "turn_left",  "angle": 15, "speed": 50}   // 左转 15°
{"action": "turn_right", "angle": 15, "speed": 50}
{"action": "pick",  "pulses": {"21": 875, "22": 395, "23": 350, "24": 250}}
{"action": "place", "pulses": {"21": 500, "22": 475, "23": 275, "24": 250}}
{"action": "stand"}                                   // 立正
```

**关键设计：forward / back 不立即执行。** 只把 `step` 累加到 `pending_forward`；
等到碰上下一个非直行动作（或 JSON 走完），才把累计距离一次性走掉。
所以连着的 9 个 `forward 100` 会合并成一段 900mm 直行，中间不停下重新对齐——
既省时间，也避免每 100mm 就重校一次航向。

转弯、夹取、放下都是即时执行。**第一次放下之后会关掉颜色微调**，之后每转一次弯计数，
累计 6 次转弯后再打开——因为放下后场地和目标位置都变了，继续跟着旧色块走会把机器人带偏。
（另外路线第 23–53 步之间也暂停颜色微调。）

## 3. 一次夹取的完整过程（NO7 带标定的真实时序）

| 时间 | 动作 | 说明 |
|---|---|---|
| +1.5 s | 量电压 | 连采 30 次（间隔 0.05s）取**中位数**，不是平均值——瞬间压降会骗人。低于 11.3V 额外多走一段 |
| +4.4 s | 摆到标称夹取姿态（pick1） | 分两批：先 21 号底座横转到位（2.2s），再 22/23/24 一起动（2.2s）。21 先转好臂再伸出去，避免抢空间 |
| ≈ +9 s | **阶段二：模型 + 雅可比精对准**（只有 NO7） | 检测 bbox 中心与标定 `anchor` 比得像素误差 `(ex,ey)`；伪逆解 `J·du = -e` 算出 21–24 各动多少，单步模长 ≤40，整臂走一次（2.2s + 0.8s）。误差进 ±3px 收工，最多 8 轮。**典型 3 轮，最坏 8 轮 ≈ 25s** |
| 人工 | 手动微调 + 回车确认 | 打印 `21=… 22=… 23=… 24=…`，敲 `22w`（该舵机 +5）、`23s10`（−10）、`a`/`d`（21 号左右 5）。空回车 = 夹，`c` = 退出 |
| +2.5 s | 夹爪闭合 | 25 号 → 700，2.0s 走完，再停 0.5s 咬稳 |
| +2.0 s | **拔起（只有第 1 次夹取）** | **22 号「肩」舵机**从复位位 705 抬到 `PULL_UP_22`，1.0s 走完，再**保持 1 秒**把目标从地里/网里拔出来 |
| +2.0 s | 恢复初始姿态 | 22/23/21/24 一条指令同时回官方初始位（1.5s），再把 25 号设成当前状态（0.5s） |

**单次夹取动作耗时**（不含人工确认）：

```

摆位 pick1      ████████                4.4 s
精对准(典型3轮)  ██████████████████      9.0 s
夹爪闭合        ████                    2.5 s
拔起 + 保持     ████                    2.0 s
恢复初始姿态    ████                    2.0 s
人工确认        ░░░░░░░░░░░░░░░░░░░░    不定
                └────┴────┴────┴────┴──
                0   2.5   5  7.5  10 s
```

合计约 **21.4 秒** + 人工确认时间。

> **整条流程不是无人值守的。** 每次夹取和放下都停下来等人敲回车。这是刻意的：现场要确认
> 夹住没有、位置对不对才继续走。跑一次完整路线需要人一直守在终端前。

## 4. 走：直行段是「100mm 粒度的小步闭环」

距离不一次走完，切成**每段最多 100mm** 的 chunk（`move_one_chunk`，`MOVE_SPEED=50`）。
每走一个 chunk 前插入两件事：

**① 颜色左右微调**（`color_keep_center`）
- 检测色块 bbox 中心 `cx`，和**这一段直行开头记下的参考中心**比（不是画面中心！）
- 偏差 > 3px 才动：色块偏右 → 右移 7mm；偏左 → 左移 10mm
  （向左力度刻意加大，补偿六足右偏）
- 一旦动了就把航向目标重设为当前 yaw——因为横移本身会带一点转向
- 整段都检测不到色块 → 把 24 号腕舵机往下压 5 个脉宽（下限 100），相当于低头找目标

**② IMU 保航向**（`update_imu` + `angle_error`）
- 积分 gz 得 yaw，和本段目标比
- 误差 > **+1.0°** → 左转；误差 < **−8.0°** 才右转——**左右阈值故意不对称**，压住六足「总往右偏」
- **转多少和误差成正比**（P 控制）：`step = clamp(err × IMU_STRAIGHT_GAIN, 1, IMU_STRAIGHT_MAX)`，
  默认 `GAIN=0.6`、`MAX=8.0`——误差大转得多、误差小转得少，不再是固定转 1°
- 转完**左右分支都对称地把目标 yaw 重设为当前值**（早先只在右偏分支重设，左偏时目标不重设、
  积分一路累加导致一直转，已修）
- **gz 取中位数，不单读一个样本**（`GYRO_FILTER_SAMPLES=5`）：`dt` 跨的是一整段
  100mm 行走（好几秒），单样本乘上几秒 `dt` 会放大成几十度的假跳变。`init_imu`(200 样本)
  和 `reset_imu`(100 样本) 本来就在滤波，只有真正在跑的 `update_imu` 漏了
- 日志行尾带 `(dt=…s rate=…°/s)`：`rate` 是这次积分用的平均角速度。**机器人站在地上
  应该是 0**，若常在 ±0.5°/s 以上，说明那次转弯后的零漂没标定准，yaw 里混着假漂移

用「相对参考点」而不是画面中心：好处是色块本身挪了位置也能跟；代价是如果色块真的移动了，
机器人会一路跟着它走。

## 5. 转：开环步数 + 只修一次 + 转完归零

`imu_turn` 的做法：

1. 目标角度拆成 **≤5° 一步**，逐步调 `turn_left/turn_right`，速度 `TURN_SPEED=30`，
   每步之间停 0.08s
2. 走完停 0.2s，连采 5 次 IMU 算出 `err = 目标 − 实测`
3. `|err| > 1°` 才补一步 1°，**且只补这一次**，不再循环
4. 最后 `reset_imu()`：重采 100 个 gz 样本重标零漂，并把 yaw 归零

**「归零」是关键。** 陀螺仪积分漂移随时间累积，一条路线要转十几次弯，一直累加跑到后面
航向就完全不可信了。既然每次转完都把 yaw 清零、目标重设为当前值，误差就不会跨段传播——
代价是每段的绝对朝向都带着上一次转弯的残余误差，靠的是「每次只转十来度、残余误差小」。

**NO7 多一步**：`reset_imu()` 之后，如果机器人上有 `models/map.npz`，就用深度相机读一帧、
对预建地图做 ICP，得到相机在地图里的真实朝向；第一次跑记下「IMU 与地图的航向偏置」，
之后每次转弯都用地图朝向覆盖漂移。这是把 IMU 从「唯一依据」降级成「备用依据」，
本质上是给长路线加一个绝对参考。

## 6. 电压补偿：因为「走多远」是开环的

六足 `go_forward(pos, 2, step, speed, 1)` 是按「走 step 毫米」下发的，但**实际步长随电池
电压变化**——电压一低，同样指令走不到那么远，机器人停在夹取点前面，夹爪自然够不着。
所以夹取/放下之前统一做一次补偿：

```python
if   voltage >= 11.3:  extra = 0            # 电压正常，不补
elif voltage <= 10.3:  extra = 80           # 很差，补满 80mm
else:                  extra = 40..80 线性插值，再乘 0.75 系数
```

另外两处快速判断（采样少、够快）：**后退**前如果电压低就多退 10mm；**左转**前如果电压低
就多转 5°（每段路线只补一次）。

## 7. 第 2 次夹取 / 放下为什么摆位不一样

| 动作 | 摆位顺序 | 耗时 |
|---|---|---|
| `pick1` | 21 → 22,23,24 | 4.4 s |
| `pick2` | 22,23 → 24 先摆到 500（抬头看）→ 21 → 24 回 JSON 值 | 8.8 s |
| `place1` | 21,22,23,24 一起到 JSON 的放下脉宽 | 2.2 s |
| `place2` | 同 place1，用第 2 个 place 的脉宽 | 2.2 s |

pick2 多出来的「24 先到 500」是为了先抬头看一眼再落位，避免臂直接撞到目标。
放下收尾是夹爪张到 400（2.0s，**越小张得越开**），然后复位。
**拔起只在 pick1 做**（`pull_up=(pick_count == 1)`），第 2 次不拔。

## 8. 状态上报与视频

`report(...)` → `communication.task_server`（import 不到就整个跳过，不影响运行），字段：
`state` / `position_m` / `heading_deg` / `picked_count` / `message`。
位置是 `advance_pose` 按 `x += dist·sin(yaw)`、`y += dist·cos(yaw)` 推出来的航位推算值。

另有后台线程每 0.1s 抓一帧推流，保证手机端一直有画面（NO7 推原图 + LAB 阈值图）。
NO6 收尾会立正 → 上报 `END` → 停 5s 供中枢确认。

## 9. 坑与注意

### ⚠️ 未结：直线阶段 yaw 的「假漂移」——IMU 报的偏比实际大得多

现场实测（2026-09-15）：一段 1000mm 直行里 IMU 报 `yaw` 从 `4.1` 漂到 `-26.8`（约 **31°**），
但**机器人实际走得基本是直的**。也就是说这一段 yaw 里很大一部分不是真实转动，是假的。

同时出现过一次物理上不可能的跳变：一次迭代里 `yaw` 从 `-26.8` 跳到 `+16.5`（**+43.3°**），
而机器人当时在直走没转。机制是 `update_imu` 拿**单个** gz 样本乘上跨整段行走的 `dt`——
已按上面的中位数滤波修掉，但**渐变的那 31° 还没定论**。

两个待查方向（都还没改）：
1. **零漂标定不准**。`reset_imu` 是刚转完弯立刻采 100 个样本，机器人可能还在晃，
   bias 偏了之后整段直行都在按这个偏差积分。看日志里的 `rate` 即可判断。
2. **`target_yaw` 重设的时机**。`target_yaw = imu_state['yaw']` 是在**发出**转弯指令之后立刻
   执行的，但此时 `imu_state['yaw']` 还没把这次转弯积分进去，**下一次** `update_imu` 才积。
   于是同一个转弯被"扣"了两次（物理上一次、yaw 上一次），循环可能反复修正同一个量。

> 改之前先确认是哪一个：光看日志的 `rate` 就能分辨（`rate` 大 = 零漂问题，`rate` 接近 0
> 但 yaw 还在持续单向走 = 重设时机问题）。

### ✅ 本次已修：拔起方向反了，夹住之后目标被往下压

原来写的是 `PULL_UP_23 = 200`，发的却是 **23 号（肘）**，而注释写的是 22。
22 号是**肩**，复位脉宽 705，**比 705 大才是上抬**——历史上两次尝试
（`705→600` 和 `23 号 200`）都是往下压的方向。

现在改成 `PULL_UP_22 = OFFICIAL_ARM[22] + 80 = 785`，并加了 `--pull-up N` 便于现场一次跑遍
几个值。方向还是反的就传 `--pull-up 625`。

> 你确认的「抬起来 → 等 1s → 放下 → 恢复初始状态」正是现在的代码形状，
> 所以拔起这套机制本身不用再改，只需要现场把方向坐实。

### ⚠️ 潜在：路线末尾那段直行的「暂停颜色微调」判断写错了变量

循环里用的是当前步号 `23 <= i <= 53`，但主循环结束后处理剩余直行的那段用的是
`23 <= len(actions) <= 53`——`len(actions)` 是总步数（88/89），永远不在这个区间，
所以末尾那段等于无条件启用颜色微调。按当前路线末尾在 76–88 步，本来也不该被暂停，
**现在没有实际影响**；但路线一改就可能和循环内的行为对不上。两个文件都有这处。

### ⚠️ 潜在：JSON 里 pick/place 缺 pulses 会直接崩

`pick1_prepare` / `pick2_prepare` / `place1_prepare` 拿到 `None` 时会去做 `None[sid]`，
抛 TypeError。当前 JSON 每个 pick/place 都带 `pulses`，所以碰不到；
只有 place2 那一支做了 `pulses or dict(OFFICIAL_ARM)` 的兜底。

### ⚠️ 现场注意：串口独占

`/dev/ttyAMA0` 同一时刻只能一个进程占。跑之前先 `sudo systemctl stop spiderpi`，
joystick 若在跑也要停。机器人是 STA 局域网模式，**IP 会变**，连不上先确认当前 IP。

### ⚠️ 现场注意：机器人上的路线 JSON 比本地新，两边已经走岔了

| | 步数 | 时间 | 关键位置 |
|---|---|---|---|
| 机器人 | 89 | 9/15 14:41 | pick 在 **54** 步 |
| 本地 | 88 | 9/14 02:37 | pick 在 **36** 步 |

不只是数值微调，**pick 的位置都挪了**。所以别用整目录同步脚本，会把机器人上这份现场调的
路线覆盖掉。
