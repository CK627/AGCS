## 3. 关键硬件事实（重要，别踩坑）

- 机械臂初始位（官方默认，用户确认过的正确位）：`21:500, 22:705, 23:90, 24:330, 25:700`
- 关节编号：`21`=底座横转、`22`=肩、`23`=肘、`24`=腕俯仰（相机装这里）、`25`=夹爪
- 摄像头 / 机械臂均已物理重装、方向正：`camera_rotate: 0`、`flip_servos: []`
- **逆运动学检测位** `setPitchRangeMoving((0,15,5), -90, -90)` 解出来是 `{21:500, 22:439, 23:80, 24:231}`，
  和上面的初始位不一致（22 差很多）——**夹取用 IK，复位用固定初始位，别混**
- `board.bus_servo_read_position()` 本机扩展板**只能写、不能读**物理脉宽
- **IMU 只有陀螺仪没有磁力计**，yaw 是 gz 按 dt 积分出来的相对值，会缓慢漂移 →
  长路线必须「每转一次弯就 `reset_imu()` 重标零漂 + yaw 归零」，误差不跨段传播
- 超声波近距离读数乱跳（-1、突跳几十 cm），**不可作主距离**，只做避障；主距离用深度相机或面积估距

### 深度相机（Astra Pro）—— 高度问题的解法

- 机器人上 `/home/pi/orbbec_sdk/` 是**自包含 OpenNI2 运行时**（配套 `libOpenNI2.so` + `liborbbec.so`），
  `agcs_lib/depth.py` 用 ctypes 直调；**系统 apt 装的 OpenNI2 不配套，枚举不到设备**
- **深度**走 OpenNI2（USB `2bc5:0403`），单位 mm
- **彩色**走 OpenCV `/dev/video0`：彩色设备 `2bc5:0501` 被内核 uvcvideo 占用，OpenNI2 的 `SENSOR_COLOR`
  会超时读不到帧，**不要走 `depth.read_color()`**
- 点云坐标约定：相机系 `X 右 / Y 上 / Z 前`（mm）；机器人系 2D `x 右 / y 前`（mm），
  绕竖直轴转 `φ = (500 - pan) * 90 / 400`（21 号舵机 500=正前、900=左90°、100=右90°）

## 7. 当前卡点 & 进行中 ⚠️

### 7.0 IMU 直线段航向发散——已定位并修，待整条路线复跑

**症状**：直线段 `yaw` 每块掉 13~16°，日志里**每条命令都是「左转」**，误差从 +13° 涨到
+17° 从不收敛，机器人一路朝左转飞，最后色块转出画面。

**病根**（有实测支撑，不是推测）：官方 SDK 的 `imu_queue = queue.Queue(maxsize=1)`，
满了就丢。`get_imu()` 拿到的是「上次取走之后到达的第一个样本」，**两次调用之间的样本
全丢**。而 `update_imu` 每 1.9 秒才取一个瞬时样本乘上整段 `dt`——那个样本落在六足步态
周期的哪个相位纯属偶然，而这段的真实平均角速度可能≈0 → 每块灌进一个随机方向的假转角。
控制器看不见自己发出的修正转了多少 → 误差永不收敛 → 一直朝同一方向发指令 → 真的转飞。

**实测依据**（`CompetitionUse/imu_probe.py`，可在机器人上复跑）：

| 测的东西 | 结果 |
|---|---|
| IMU 出数速率 | 约 **105 Hz**（紧循环每 9.5ms 取到新样本，不是陈旧数据） |
| 量纲 | **°/s**（静止零漂 0.75°/s、噪声 ±0.15°/s） |
| `ik.turn_left(20°)` 密集积分 | **+13.26°** → **符号没反**，`IMU_DIRECTION_SIGN=1` 是对的 |
| 静止 2 秒按真实间隔积分 | **+0.020°** → 积分方法本身没错 |

**修法**：新增 `agcs_lib/imu.py` 的 `ImuTracker`，后台线程约 105Hz 连续读队列、按真实
样本间隔积分。单样本间隔几毫秒，坏样本可忽略——原来的 +43.3° 假跳变和 +94° 幻影在架构
上消失。另加 `--imu-straight on|off` 便于 A/B，`IMU_SETTLE_S=0.25` 保证重标零漂时机身已稳。

> ⚠️ **中途有一版错诊断已回退**：曾把病根归给「零漂标定不准」，加了中位数滤波
> （`GYRO_FILTER_SAMPLES`）+ `dt` 钳位 + 直行段前重标零漂。**现场跑下来更糟**已整体回退
> （`b7d1367`）。中位数滤波只是让那个**选错的**样本更"干净"，救不了采样太稀。
> 具体见 `CompetitionUse/NO6-NO7-流程说明.md` §9。

> ⚠️ **后台线程不会跟舵机抢串口**：`get_imu()` 只从队列取数（队列由 SDK 自己的
> `recv_task` 线程填充），不写串口；舵机指令走 `buf_write()` 的写路径，两者不共享锁。
> 早先判断「线程有风险」是错的。

**还没结的**：`target_yaw` 在发出转弯指令后立刻重设，目标基准会永久落后所修正的角度
（每次约 5°）。另外开环转弯重复性差（同样 `turn_left(20°)` 两次实测 +13.26° 与 +6.09°），
所以**别**据一次小转的结果去改 `GYRO_SCALE_*`。

### 7.0.1 直线段「先直、然后一路往右偏」——两处方向性偏置（已改，待复跑）

修完 7.0 之后症状变了：IMU 不再把机器人一路带向左，但直线段变成**先走直、然后持续右偏**。
复查代码找出两处都会把机身稳态推离目标航向的偏置：

1. **航向死区左右不对称，而且方向写反了。** `angle_error` 是 `(target - current)`，所以
   `err > 0` = 机身朝右歪（该左转）、`err < 0` = 机身朝左歪（该右转）。原代码
   `err > LEFT_TOL(1.0)` 才左转、`err < -RIGHT_TOL(8.0)` 才右转——**实际效果是「机身朝左
   歪 8° 都不管」**。机身长期歪着 → 装在身上的相机跟着歪 → 画面里色块恒偏一侧 →
   颜色微调持续往那一侧平移。已改成单个对称常数 `TURN_TOL_DEG = 3.0`，现场可 `--turn-tol` 调。
2. **每次颜色微调都重置航向基准。** `move_straight_imu_color` 里
   `if color_adjusted: target_yaw = imu_state['yaw']` 把这一小段已攒下的航向误差一笔勾销，
   误差永不收敛。颜色微调是**平移**、不改变航向基准，已删掉这行重置。

> ⚠️ 这两处解释的是**航向**偏置。如果实测的右偏其实是**平移**（机身朝向没变、整体横着滑），
> 陀螺仪根本看不见，这两处改动就救不了——那要去查六足步态的横向分量或颜色微调的力度。
> 复跑后看日志里 `error=` 的分布：**若误差一直在 ±1° 内而机器人仍右偏，就是平移问题。**

**运行日志现在会落盘**：`logs/<日期>/autocapture/<时-分>.log`（整段 stdout + stderr 抄一份）。
之前 `print()` 只进终端、不落盘，官方日志只收 `action_msg`，所以几次现场排查都因为
没留下完整日志只能靠猜。

### 7.0.2 航向目标被自己重置 —— 「右转严重」的真凶（已改，待复跑）

7.0.1 改完再跑（日志 `logs/2026-9-15/autocapture/18-47.log`），症状变成**右转严重**。
日志一行就露馅了 —— **`target` 在一次直行段内自己往上爬**：

```
IMU yaw=6.9  target=3.0  error=-5.0  -> 右转3°
IMU yaw=9.5  target=6.6  error=-3.8  -> 右转2°
IMU yaw=12.3 target=9.6  error=-4.2  -> 右转3°
IMU yaw=15.8 target=12.3 error=-5.2  -> 右转3°
```

目标每块涨约 3°，**正好等于幻影漂移量**。一次直行段里目标本该固定，它却跟着 yaw 跑。
根因是 `move_straight_imu_color` 里修正转向之后**还有一处** `target_yaw` 重设：

```python
if corrected:
    time.sleep(0.05)
    target_yaw = imu_state['yaw']    # ← 真凶
```

7.0.1 只删了「颜色微调后」那一处，**漏了这处**（它当时被记在 7.0 的「还没结的」里，
判断「不对称阈值盖得住」——死区改对称后立刻暴露）。修正是「把 yaw 拉回本段目标」，
修完把目标挪到当前 yaw，等于宣告刚才的偏差不算数，控制器此后只修「距上次修正之后的
新偏差」，永远清不掉已有偏置 → 每块发一次右转 → **右转严重**。已删。两处都不能重设。

**同时更正一个错误判断**：零漂标定**没有错**。真机实测（`/tmp/bias_warmup.py`，只读）：

| 开机后 | 标定出的零漂 |
|---|---|
| 0.5s | −1.917°/s |
| 1.5s ~ 30s | −1.911 ~ −1.915°/s |

**稳定不漂**，既不是冷启动漂移，也不是标定时机身没静。`init_imu` 标出的 −1.914 与
实测 −1.913 一致——标定是对的。（曾据「静止零漂 0.75°/s」的旧数字判断标定错了，错。）

**但走路时 `rate` 稳定 +1.6~1.8°/s**，即站着与走路差 1.8°/s。**已判明，是 (a)：机身真转。**

### 7.0.3 定论：`rate` 不是幻影，是步态真转；「右转严重」= 棘轮把修正吃掉了

三个候选全部用真机测量排除，最后逐动作归因定案。

**排除过程（每一项都是实测，不是推理）：**

| 候选 | 测法 | 结果 | 结论 |
|---|---|---|---|
| 零漂自己漂走 | `/tmp/bias_long.py` 静止 5 分钟 | +0.2441 → +0.2183°/s，极差 0.029 | 排除。信它 5 分钟才攒 5.5° = −0.018°/s |
| 标定时机不对 | `init_imu` 在 `restore_travel` **之前**（609 vs 627） | 标定时无任何舵机动作 | 排除，标定窗口是干净的 |
| 转向符号反了 | `imu_probe.py --sign --angle 3 --reps 4` | 左转 +1.18 / 右转 −2.87 | 排除。右转 3° 实测 −2.87°，方向幅度都对 |
| `left_move` 偷偷带转 | `--lateral`（孤立） | 左移 **+0.64°**、右移 +0.96° | 见下 |

**逐动作归因（`imu_probe.py --segment`，复刻真实节奏「左移 10mm → 前进 100mm」）：**

| 动作 | 孤立测 | 夹在前进中间测 |
|---|---|---|
| `left_move` 10mm | **+0.64°**（3 次：+0.61/+0.66/+0.65） | **−1.01°**（3 次：−1.13/−0.93/−0.98） |
| `go_forward` 100mm | −0.56°（−0.54/−0.30/−0.84） | **−1.32°**（−0.96/−1.62/−1.39） |

**同一个 `left_move`，孤立做是 +0.64°，夹在前进中间做是 −1.01°——符号都反了。** 而每个
会话内又高度一致（±0.05）。所以真相不是「某个动作固定带转」，而是：

> **这台六足每做一个腿部动作，航向就产生约 ±1° 的偏转，方向随会话/站姿/腿相位而变，
> 会话内稳定。** 一个 1000mm 直行段有 19 个腿部动作（10 次走 + 9 次横移），累积
> 12.8° 完全在这个量级内。

**所以日志里的 `rate=+1.6°/s` 是真转，IMU 一直在说真话。**「右转严重」的成因是那个
已被删掉的目标棘轮，机制是：

```
每个 1.5s 窗口：机身真漂约 +2.4°
控制器：err 涨到 3° → 发一次右转 3° → 然后 target_yaw := 当前 yaw
                                       ↑ 已漂掉的 2.4° 被一笔勾销，err 从 0 重新攒
```

机身在持续左漂，控制器每轮只刹一次、刹完就把账清零 —— **永远差着，永远在转**。
7.0.2 删掉两处重置后，err 会真正累积到 12.8°，控制器就能一路把它压回死区内
（单次修正 ≈3° > 每块漂移 ≈1.3°，有净余量，收敛）。

**剩下的固有噪声**：颜色环每个直行块都发一次横移，横移自带 ±1° 航向噪声，正好加在
IMU 要控的那个量上。若复跑后仍见小幅来回，先考虑**降低颜色微调频率**（如每 2~3 块才
调一次，或调大 `COLOR_CENTER_TOL`），而不是继续加大 IMU 增益——两个环在互相打架。

### 7.1 拔起脉宽现场坐实

第一次夹取后要把目标从地里/网里**拔起来**，动的是 **22 号「肩」**（不是 23 号肘）。

**方向基准是「夹取位」，不是复位位 705。** 这点极易搞错：拔起发生在夹爪闭合之后，
此时 22 号停在路线 JSON 的夹取位（当前路线 `22:395`），`restore_travel` 还没跑。
所以「往上抬」= 把 22 调到**比夹取位大**。

现场证据：`785` 那次抬得太高，对应 395→785（**+390**）——方向对、幅度太大。
当前值 **`PULL_UP_22 = 450`**，即 395→450（**+55**，小幅抬）。

> 历史记录里「`705→600` 方向反了」与上面的基准对不上（600 比夹取位 395 大，按现在
> 的基准是往上抬）。多半是当时拔起发生在 `restore_travel` 之后、基准是 705。
> 总之**看当前这一刻 22 号在哪**，别照搬历史结论。

两个脚本都留了 `--pull-up N`，**幅度不合适直接命令行试值，不用改代码**。
运行时打印真实起止与抬升量：`拔起：22 号肩舵机 395 → 450（抬升 +55）`。

### 7.4 `1.py`：NO6 寻路 + YOLO 夹取（临时测试）

**起因**：路线固定距离每次跑都会差一点（前后都差、量不大），怀疑打滑 / 步态开环。
试的思路 —— **寻路照旧，夹取不再靠「走到录制点」，改成看着画面夹**。

`CompetitionUse/1.py` 的做法是**不复制代码**：用 importlib 把 `Auto-capture-1.py`
当模块加载，只把里面的 `do_pick` / `run_calibrate` 猴补丁成 YOLO 版。
（文件名带连字符是非法模块名，普通 `import` 做不到，所以走
`importlib.util.spec_from_file_location`。）好处是 NO7 寻路那一大段（IMU 航向、颜色微调、
电压补偿、放下、上报、运行日志）一行都不用重写，以后修 NO7 时 1.py 自动跟着走。

| | 寻路（走/转/航向/颜色） | 夹取 | 放下 |
|---|---|---|---|
| NO6 `Auto-capture.py` | 读 JSON | 读 JSON 的 pick 脉宽 | 读 JSON |
| NO7 `Auto-capture-1.py` | 读 JSON | JSON 脉宽 + 雅可比精对准 | 读 JSON |
| **`1.py`** | **读 JSON（与 NO6 相同）** | **不读 JSON，YOLO 找目标** | **读 JSON** |

**⚠️ 最大的坑：YOLO 靠近会把「里程」走乱。**
`yolo_approach()` 是看着画面走的，它走了几步、实际走了多远，路线并不知道：

- **朝向不会坏**：每个直行段开头都 `target_yaw = imu_state['yaw']`，每次转弯后都
  `reset_imu()`，一律以「当前朝向」为新基准，相对转角照常有效。
- **距离会偏**：夹取点之后那些 forward/back 的距离基准已经不准，夹取点离放下点越远
  偏得越多。想减小就调小 `--stop-w`（少走点）或 `--step-mm`。

**夹取起点姿态是内置的，不看 JSON**（`1.py` 顶部 `PICK_PULSES`）。数值参考原路线夹取位，
但 **21 号底座横转从原路线的 875 / 705（偏左）改成 500（正前）** —— YOLO 是转机身把目标
对到正前方的，机身正对目标时臂也该朝正前伸。**这个必须现场用微调确认**（`a`/`d` 调 21，
`22w`/`22s`、`23w`/`23s`、`24w`/`24s` 调其它，回车夹取），试出来的好值直接改文件顶部
常量，不碰 NO6/NO7。

**当前机器人上没有 `calib_pick*.json`** → 雅可比精对准会跳过，直接进手动微调。
想启用先跑 `python3 1.py --calibrate 1`。这个也猴补丁了：在 **YOLO 起点姿态**上标定，
而不是 NO7 原版那样在 JSON 脉宽上标 —— **标定姿态必须和实际夹取姿态一致**，否则雅可比
是在别的姿态下量的，精对准会用错方向。

**路线事实**（机器人上 89 步那份）：只有 `turn_left`(21 次) **没有 `turn_right`**；
`forward` 60、`back` 4；两次 pick 在第 **11** 步（`21=875`，目标在左侧）和第 **55** 步
（`21=705`）；两次 place 在第 **21 / 66** 步。

**YOLO 找不到目标时默认跳过夹取**（`FALLBACK_TO_JSON_ON_MISS = False`），不退回 JSON
脉宽 —— 回退等于把测试又拉回固定路线，结论会被污染。想硬夹再打开这个常量。

常用跑法：

    python3 1.py --color red                 # 其余参数原样透传给 NO7
    python3 1.py --color red --stop-w 170    # 让 YOLO 走得更近再夹
    python3 1.py --color red --max-steps 0   # 只居中不前进，单独验证检测/居中

## 8. 用户反复强调的算法原则（别违背）

- **不硬编码距离 / 步数 / 固定夹取点**，要闭环、按实时画面自动调整
- **检测到颜色就锁定，不转圈**；不居中 / 不正就主动调整，不要 skip
- **夹取前先看一眼距离**；目标略超可及范围就前进微调，不轻易放弃定点夹取
- **高处目标要有保底**（体态升降 + 抬头检测）
- 官方 `block_fetch.py` / `intelligent_fetch.py` / `color_track.py` 是可靠参考

> 注意 §2.5 那两个脚本是**固定路线 + 固定脉宽**的比赛演示，和上面这条原则是两套东西：
> 原则针对自主寻路/夹取（`agcs_lib/search.py` + 深度 3D 抓取），别拿原则去改比赛脚本的路线设计。
